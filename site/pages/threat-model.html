Protected against

  • Someone copies the server's databaseCovered

    They get ciphertext and hashes. Titles, text, tags, folder names and app names are encrypted on your device with keys the server never has. The database holds hashes of sign-in keys and tokens, not the keys.

  • SYNOVAX itself wants to read your memoriesCovered

    It cannot with what it stores: the vault key is made in your browser and only ever stored wrapped by keys from your passphrase or your 24 words. (It serves the page's code, though: see "A changed web page" below.)

  • Someone listens on the networkCovered

    Everything that leaves your device is already encrypted, inside an HTTPS connection. A listener sees sizes and timing at most.

  • A connected app reaches for folders it was not givenCovered

    Folder keys are wrapped for an app only when you grant the folder, so it holds no key for any other, and the server refuses the request as well.

  • A connected app tries to write, change or deleteCovered

    No request lets an app change or delete a memory. It may only suggest one, if you turned that on; the suggestion waits in your inbox until you approve it, at most 30 an hour per app and 500 waiting.

  • The server hands an app a public key of its own, to read suggestionsCovered

    The connector checks the vault's public key against an HMAC your vault made with the app's own secret, which the server never has. A swapped key fails the check and nothing is sealed.

  • An app you took a folder from keeps reading itCovered

    Taking a folder away, or revoking the app, gives the folder a new key in your browser and encrypts every memory in it again. The old key opens nothing stored now. What it read before, it keeps.

  • A leaked or stolen app keyCovered

    Revoke it in your vault. The server deletes its token hash and wrapped folder keys, and the key fails on its very next request. Other apps keep working: every app has its own key.

  • An encrypted record is moved or swappedCovered

    Every ciphertext is bound to its record with authenticated data. A memory moved under another id, or a key moved to another folder, does not decrypt.

  • The read log is edited afterwardsCovered

    Each hour of reads is sealed into one Merkle root. A changed entry no longer matches its seal, and you can check any sealed entry against it in your browser.

  • Old seals are rewritten or droppedCovered

    Seals form a hash chain. Your vault remembers the newest seal it saw in each browser and checks that the chain still leads from it; a webhook copy (SEAL_PUBLISH_URL) keeps the chain somewhere the server cannot edit.

  • An email, chat or import carries instructions written for your AICovered

    Before any model sees a memory, the connector drops invisible characters, replaces instruction overrides, fake system messages, requests to send data or money away, tool calls, jailbreak phrases and hidden or encoded text with a marker, and quotes the rest as data. Imports leave such memories out unless you take them. Every catch is in your read log. The rules catch common shapes, not every attack: the public test on the immune page shows how they do.

  • The server swaps keys when you share a folder or name an heirCovered

    The share code carries a fingerprint of the other vault's key, and your vault checks the key the server returns against it. The sealed box is also tagged with a key only your two vaults can make, so the server cannot forge a share or a legacy.

  • Guessing passphrases or the 24 words through the serverCovered

    Failed attempts are limited per name and address (10 a minute for a passphrase, 5 per 10 minutes for the words), with a cap per vault an hour. The limits are kept in the database, so a restart does not reset them.

  • Finding out which vault names exist, at sign-inCovered

    The salt question gets a made-up but stable answer for names that do not exist, and every vault uses the same number of rounds. (Creating a vault still says when a name is taken: see below.)

  • Another site sends requests in your nameCovered

    Sign-in rides in a header the page sets, not in a cookie, so a request from another site carries nothing.

  • Scripts injected into the page, or the page framedCovered

    A strict content security policy allows only SYNOVAX's own scripts, no inline scripts, and no framing. Text from the server is placed with textContent, never as HTML.

  • A lost phone with your authenticatorCovered

    The 24 words open the vault and turn two-step sign-in off. Signed-in devices lets you end any session; changing the passphrase ends all the others.

  • A two-step code seen over your shoulderCovered

    Each code works once: the server accepts only a time step newer than the last one used.

Not protected against

Said as plainly. Some are limits of any web app, some are on the list for later.

  • A weak passphrase and a stolen databaseNot covered

    With a copy of the database, someone can try passphrases offline, at the cost of 600,000 PBKDF2 rounds per guess. A long passphrase makes that hopeless; a short one does not.

  • Malware on the device where you open the vaultNot covered

    Whatever can read your screen or your browser's memory can read what you can read. Encryption protects the vault on the server and on the network, not on a compromised device.

  • A changed web pageNot covered

    The encryption code is delivered by the site, as with any web app. Someone who controlled the site could serve different code. The code is open source so it can be compared, and you can run your own copy.

  • What an AI app does with what it has readNot covered

    Once an app reads a memory, that text is in the app's hands and its own policies apply. The read log tells you exactly what it got.

  • Hidden instructions the rules do not knowNot covered

    The checks match known shapes. A new wording can get past them; it then reaches the model still quoted as data, and how a model treats quoted data is up to that model.

  • Losing every way inNot covered

    Without the passphrase and the 24 words, nobody can open the vault. There is no reset.

  • MetadataNot covered

    The server sees your vault name, counts, sizes and times, which app may read which folder, and the read log. It needs these to run.

  • A server that hides a read from the logNot covered

    Seals prove that logged entries were not changed or removed later. They cannot prove that a dishonest server wrote every request down in the first place.

  • Seals rewritten before anyone kept a copyNot covered

    Without a webhook copy and before any browser saw them, a server could rewrite its whole history. Seals are not published on a blockchain.

  • A server that opens a legacy earlyNot covered

    The server decides when you have stayed away long enough. Working with your heir, a dishonest server could hand over the sealed key early. Name only someone you would trust with your vault anyway.

  • What a vault you share with keepsNot covered

    Stopping a share cuts off future reads and replaces the folder key, but what the other vault already read, it has.

  • Deleted data in backupsNot covered

    The server's automatic database copies keep deleted ciphertext until they rotate out, about three and a half days with the default settings.

  • The two-step secret on the serverNot covered

    The server must read it to check codes, so it is encrypted with a key from the server's own secret file, not yours. Someone with the database and that file could make codes; they would still need your passphrase, which the server does not have.

  • Learning that a vault name is takenNot covered

    Creating a vault says "That name is taken" for a name in use. It cannot be avoided while people pick their own names.

  • BugsNot covered

    This is early software. It is open source and tested on every change, and it has not had an independent audit yet.

What you can do yourself

  • Use a long passphrase, and keep the 24 words on paper, somewhere safe.
  • Turn on two-step sign-in in Settings.
  • Give each app only the folders it needs, and look at the read log now and then.
  • Revoke an app the moment you stop using it, or if its key may have been seen.
  • Found a security problem? Report it privately, as described on the security page.
