Open standard · version 1.0.0

Build your ownvault or checker

How a SYNOVAX vault keeps memories, how its keys work, what a connector may do, what the read log records, how it is sealed, and how memories are handed to a model. The reference code is three files in shared/; the test vectors are made from that code and checked against it on every test run.

Conventions. Bytes in text are base64url without padding, unless a field says hex (lowercase). Strings are UTF-8; JSON inside a ciphertext is compact, as JSON.stringify writes it. Times are milliseconds since the Unix epoch. Ids are 16 random bytes in base64url (22 characters). Primitives: AES-256-GCM, HKDF-SHA256, PBKDF2-SHA256, SHA-256, HMAC-SHA256 and ECDH on P-256, all from WebCrypto, so the same code runs in a browser and in Node.

1. Memories and folders

A vault holds folders; every memory is in exactly one folder.

Folder
id; meta: { "name" } encrypted with the folder key, record folder:<id>:meta; wrappedKey: the folder key (32 random bytes) encrypted with the vault key, record folder:<id>:key.
Memory head
{ "title", "tags", "snippet", "source" } encrypted with the folder key, record memory:<id>:head. snippet is the first 240 characters of the text, so a connector can search without reading every body. source says where it came from (import, an app's name), or is absent.
Memory body
{ "title", "body", "tags", "source" } encrypted with the folder key, record memory:<id>:body.
App
meta: { "name", "secret" } encrypted with the vault key, record app:<id>:meta (the secret is kept so the owner can grant new folders later); for each granted folder, the folder key encrypted with the app's wrap key, record app:<app id>:folder:<folder id>.

The server stores ids, the ciphertexts above, which folder a memory is in, and times. Limits: 200 folders, 20,000 memories and 50 apps per vault; a head of at most 8,000 characters of ciphertext, a body of at most 1,500,000.

2. Keys

HKDF here is HKDF-SHA256 with a salt of 32 zero bytes, the info string given, and 32 bytes of output.

Key layout
passphrase ──PBKDF2-SHA256, 600,000 rounds, 16-byte salt──▶ master
      master ──HKDF "vault/auth/v1"──▶ authKey   (sent; the server keeps SHA-256)
      master ──HKDF "vault/kek/v1"───▶ kek       (never leaves the device)

      24 words ──index in the 256-word list──▶ 24 bytes ──HKDF "vault/recovery/v1"──▶ master
      master ──▶ authKey / kek, as above

      vault key   32 random bytes   wrapped by kek, record "vk/passphrase"
                                    wrapped by the recovery kek, record "vk/recovery"
      folder key  32 random bytes   wrapped by the vault key, and by each granted app's wrap key
      inbox keys  ECDH P-256        private key (PKCS#8) wrapped by the vault key, record "box/private"

      app secret  32 random bytes ──HKDF "vault/app/auth/v1"──▶ token (base64url; the server keeps SHA-256)
                                  ──HKDF "vault/app/wrap/v1"──▶ wrap key
                                  ──HKDF "vault/app/vouch/v1"─▶ vouch key

The passphrase is normalized (NFKC) before PBKDF2. The recovery phrase is 24 words, each the index of a byte in the 256-word list in shared/wordlist.js: 192 bits. The passphrase and recovery checks the server keeps are SHA-256(authKey) in hex.

App keys are written vlt_app.<app id>.<base64url secret>. An app proves itself with Authorization: Bearer a.<app id>.<token>.

Vouching for the inbox key. The vault computes HMAC-SHA256(vouch key, "<app id>|<inbox public key>") and stores it with the app. A connector must check it before sealing anything to a public key the server handed it.

3. Envelopes and sealed boxes

An envelope is AES-256-GCM with a fresh 96-bit IV and a 128-bit tag, the additional authenticated data naming the exact record:

Envelope
v1.<base64url( IV ‖ ciphertext ‖ tag )>

An envelope moved to another record fails to open. The record names in use: vk/passphrase, vk/recovery, box/private, folder:<id>:key, folder:<id>:meta, memory:<id>:head, memory:<id>:body, app:<id>:meta, app:<app id>:folder:<folder id>.

A sealed box is data for a vault that is not open (a suggestion), sealed to the vault's inbox public key R:

Sealed box
ephemeral pair (e, E) on P-256
      shared = ECDH(e, R)                                   32 bytes
      key    = HKDF(shared, "vault/box/v1|" + E + "|" + R)  E and R as base64url SPKI
      sealed = envelope(key, JSON, record "box")
      format   box1.<E>.<envelope>

4. The connector

A connector holds one app key and runs where the owner chooses. It fetches ciphertext with the app's token, unwraps the folder keys granted to it with the app's wrap key, and decrypts, searches and seals on its own side. The routes are in the API reference; the tools are:

ToolWhat it doesLogged as
list_foldersThe granted folders, by name.folders
search_memoriesSearch over decrypted heads, by words and by meaning, on the connector's side.list
read_memoryOne memory in full.read
suggest_memoryA sealed box to the inbox key, after checking the vouch.suggest

Every memory text a connector hands to a model must first go through part 7. No route lets an app change or delete a memory.

5. The read log

Every request an app makes is one entry of the owner's read log:

id
16 random bytes, base64url.
ts
When, in milliseconds.
vault_id
The vault.
app_id
The app.
action
folders (listed folders), list (read the heads of one folder or * for all), read (read one memory), suggest (sent a suggestion), caught (the connector removed hidden instructions from a memory).
target
The folder id or *, the memory id, the suggestion id, or null.
salt
16 random bytes, base64url. Without it the leaf cannot be tied to the entry.
The leaf
data = JSON.stringify([id, ts, vault_id, app_id or null, action, target or null, salt])
      leaf = SHA-256( 0x00 ‖ UTF-8(data) )

Because the action is in the leaf, an entry cannot later be passed off as another kind without breaking its proof.

6. Seals and the chain

Merkle rules
node = SHA-256( 0x01 ‖ left ‖ right )
      An odd node at the end of a level moves up unchanged.
      A proof lists siblings bottom up, each with its side: R (the sibling is on the right) or L.

Time is cut into periods (one hour by default). When a period ends, every entry of that period, from every vault on the server, becomes a leaf in the order it was written, and the root is the seal of that period. A period with no reads has no seal. Seals are numbered from 1.

The chain hash
prev  = chain of the seal before, or 64 zeros for seal 1
      chain = SHA-256( 0x02 ‖ UTF-8(JSON.stringify(["seal/v1", seq, periodStart, periodEnd, root, count, prev])) )

A server publishes every seal (GET /api/seals), and the proof of any leaf (GET /api/seals/<seq>/proof?leaf=), and keeps the leaves of past seals after an account is deleted, so other vaults' proofs keep working. A checker that kept any later chain hash notices an earlier seal being changed or dropped.

7. Hidden instructions

Text from outside can carry instructions written for an AI. Before a connector hands memory text to a model, it must:

  1. Normalize the text (NFKC) and drop invisible characters: zero-width characters, direction controls, the soft hyphen and Unicode tag characters, keeping a zero-width joiner inside an emoji and tag characters that complete a subdivision flag.
  2. Read it in lower case with look-alike Cyrillic and Greek letters mapped to Latin ones, and find the kinds override, role, exfil, tool, payment, jailbreak, hidden (styling that hides text) and encoded (base64 of 20 or more characters that decodes to text another rule flags). The patterns are the reference code's and may grow in a minor version.
  3. Replace each finding, with the paragraph around it (or the sentence, in a paragraph over 600 characters; or the whole HTML comment it is in), by [removed by SYNOVAX: looked like <kind>].
  4. Quote each memory between <<data CODE>> and <<end CODE>>, CODE being 6 random bytes in hex, new for every answer, after a note saying the text is data and never instructions. Any <<end CODE>> inside the text has its code replaced.
  5. Tell the server the id of each memory it removed something from, once per version (POST /api/app/caught), so the owner's log has a caught entry. Never the text.

A server may run the public hourly test: 14 attacks, each in 7 disguises, placed among ordinary memories with choices seeded by SHA-256("immune/v1|" + hourStart), run through step 1 to 4, and counted as held when the attack's marker no longer reaches the model's input. A round's hash is SHA-256(JSON.stringify(["immune/v1", hourStart, total, held, [[strain, disguise, held], …], prev])) in hex, prev being the hash of the round before (64 zeros for the first).

8. Test vectors and versioning

shared/vectors.json has three parts. input holds the fixed passphrase, salt, words, app secret, log entry, leaves and texts every vector starts from. deterministic holds values that follow from their inputs alone: the passphrase and recovery keys, the app key's token, wrap and vouch keys and its vouch, a leaf and its data, a Merkle root and proof, a seal chain hash, and the guarded and quoted text of part 7; another implementation must produce them byte for byte. sealed holds an envelope and a sealed box made with fresh randomness; another implementation must open each with the key given and get the plaintext listed.

Terminal
npm run test:vectors   # the code still produces every vector
      npm run vectors        # write them again (sealed values are kept)

The version follows semantic versioning. A change that makes data written by an older version unreadable, or changes a deterministic vector, is a new major version. Every format string carries its own version (v1., box1., vault/…/v1, seal/v1, immune/v1), so old and new data can be told apart.
