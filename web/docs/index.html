00 · basics2 min

What SYNOVAX is

One place for what your AI apps should know about you, locked so that only you and the apps you choose can read it.

Every AI app you use starts from zero. You explain your job, your stack, your diet, how you like answers, over and over. SYNOVAX keeps those facts in one vault. Apps that speak MCP (Claude Desktop, Cursor, Windsurf, VS Code and others) can read the folders you allow, and only those.

Encrypted on your device

Memories are locked in your browser before they are sent. The server stores ciphertext.

Read only where you allow

Each app gets its own key and a list of folders. Everything else stays locked for it.

Every read sealed

Each read is logged, and every hour the log is folded into a fingerprint you can check.

00 · basics3 min

The words you need

Ten words cover the whole product. You will see all of them in the vault.

Vault
Your account. It has a name (3 to 32 characters) and holds everything else.
Passphrase
What you type to open the vault. It never leaves your device; it is turned into keys in the browser.
Recovery phrase
24 words shown once when you create the vault. The only way back in if you forget the passphrase.
Folder
A group of memories with its own key, like About me or Work. Access is given per folder.
Memory
One fact: a title, a body and tags. Encrypted with its folder's key.
App key
A key for one AI app, shaped like vlt_app.<id>.<secret>. It opens only the folders you ticked.
Connector
A small program on your computer that your AI app talks to. It fetches ciphertext and decrypts it locally.
Inbox
Where memories that apps suggest wait for you. Nothing is saved until you approve it.
Read log
A line for every time an app touched your vault: which app, what it did, when.
Seal
Once per period (one hour by default) every log line is folded into one hash, a Merkle root, that is published.
01 · first steps3 min

Run it

The server has no dependencies to install. You need Node.js 22.13 or newer (it is tested on Node 24 and 26). Search by meaning in the connector is optional and is the one thing that needs npm install.

  1. Check Node

    Open a terminal and check the version. If it is older than 22.13, install the current LTS from nodejs.org.

    terminal
    node --version
  2. Start the server

    From the project folder. There is no npm install step.

    terminal
    npm start
  3. Open the vault

    Go to http://127.0.0.1:8787/vault/. The landing page is at / and these docs at /docs/.

Only on this computer by default

The server listens on 127.0.0.1, so nothing outside your machine can reach it. Level 05 covers putting it online.

01 · first steps4 min

Create your vault

  1. Choose “Create vault”

    Pick a vault name. It is the only thing the server knows you by, so it does not need to be your real name.

  2. Set a passphrase

    At least 10 characters. Longer is much better: four or five unrelated words beat a short password full of symbols.

  3. Wait a second

    Your browser runs 600,000 rounds of PBKDF2 to turn the passphrase into a key, then makes your vault key, inbox keys and recovery phrase. This is on purpose: it makes guessing slow for anyone else too.

  4. Write down the 24 words

    They are shown once. Write them on paper, in order, and keep them somewhere safe. Tick the box to enter your vault.

Nobody can reset your passphrase

Not the server, not us. If you lose both the passphrase and the 24 words, the vault cannot be opened by anyone. That is the price of the server never holding your keys.

Good passphrase, fast

Pick five random words from a book page, add a number you will remember. Store it in a password manager if you use one.

01 · first steps4 min

Folders and memories

Folders are how you decide what each app may read, so think of them as permission groups first and topics second.

Make folders

Type a name under Folders in the sidebar and press +. Rename or delete a folder from the top of its list. Deleting a folder deletes its memories too, and there is no undo.

About me

Name, language, location, how you like answers.

Work

Role, stack, projects, team conventions.

Health

Allergies, routines. Grant it to as few apps as possible.

Write memories that help

Press New memory, pick a folder, write a title and a body, add tags separated by commas. Short, specific facts work best because apps search by words.

vague

“I like coding.”

useful

“Prefers TypeScript, strict mode, no default exports. Tests with Vitest.”

Search

The search box filters by title, body and tags, inside the selected folder or across all of them. It runs in your browser on the decrypted text.

02 · connect your ai3 min

Make an app key

  1. Open Apps

    In the vault sidebar, choose Apps, then Connect a new app.

  2. Name it and tick folders

    Use the app's name, like Claude Desktop. Tick only the folders it needs. Optionally allow it to suggest memories to your inbox.

  3. Create the key and copy the config

    The key and a ready-made MCP config appear once. When the server runs on your own computer, the config already contains the right path to the connector.

Treat the key like a password

Anyone with it can read the folders you granted. Use one key per app, so you can revoke one without touching the others.

02 · connect your ai5 min

Claude, Cursor, Windsurf, VS Code

Every MCP app needs the same three things: run node, point it at connector/index.js, and pass your key and server address as environment variables. Only the file and its wrapper differ.

Settings → Developer → Edit Config. That opens claude_desktop_config.json (on Windows in %APPDATA%\Claude\, on macOS in ~/Library/Application Support/Claude/). Paste, save, then quit and reopen Claude Desktop.

claude_desktop_config.json
{
  "mcpServers": {
    "synovax": {
      "command": "node",
      "args": ["C:\\path\\to\\synovax\\connector\\index.js"],
      "env": {
        "VAULT_APP_KEY": "vlt_app.<id>.<secret>",
        "VAULT_URL": "http://127.0.0.1:8787"
      }
    }
  }
}

Cursor reads ~/.cursor/mcp.json for every project, or .cursor/mcp.json inside one project. You can also open it from Cursor's settings under MCP. Same shape as Claude's.

~/.cursor/mcp.json
{
  "mcpServers": {
    "synovax": {
      "command": "node",
      "args": ["/path/to/synovax/connector/index.js"],
      "env": {
        "VAULT_APP_KEY": "vlt_app.<id>.<secret>",
        "VAULT_URL": "http://127.0.0.1:8787"
      }
    }
  }
}

Windsurf keeps its MCP servers in ~/.codeium/windsurf/mcp_config.json, reachable from its settings under MCP. Same shape again; refresh the server list after saving.

~/.codeium/windsurf/mcp_config.json
{
  "mcpServers": {
    "synovax": {
      "command": "node",
      "args": ["/path/to/synovax/connector/index.js"],

        "VAULT_APP_KEY": "vlt_app.<id>.<secret>",
        "VAULT_URL": "http://127.0.0.1:8787"

  }
}

VS Code uses .vscode/mcp.json in your workspace, with a servers key and an explicit type. Start the server from the file's inline controls, then use it from Copilot Chat in agent mode.

.vscode/mcp.json
{
  "servers": {
    "synovax": {
      "type": "stdio",
      "command": "node",
      "args": ["/path/to/synovax/connector/index.js"],
      "env": {
        "VAULT_APP_KEY": "vlt_app.<id>.<secret>",
        "VAULT_URL": "http://127.0.0.1:8787"

Paths and menus

Use the absolute path to connector/index.js; on Windows, double every backslash inside JSON. Apps move their settings between versions, so if a menu name differs, look for “MCP” in that app's settings.

Keep keys out of git

A project file like .vscode/mcp.json or .cursor/mcp.json can end up in a repository. Prefer the user-level file, or add the project file to .gitignore.

02 · connect your ai4 min

What the AI can do

The connector gives the app four tools. Apps decide on their own when to call them; you can also ask directly.

ToolInputsWhat it does
list_foldersnoneNames of the folders this app may read.
search_memoriesquery, optional folderFinds memories by words, decrypted on your machine. Empty query returns the most recent.
read_memoryidReads one memory in full. Every read lands in your read log.
suggest_memorytitle, body, optional tags, folder, reasonSends a new memory, sealed to your vault, to your inbox. Only if you allowed suggestions.

Prompts that work

  • “Check my vault for anything about my stack before you answer.”
  • “What do you know about me from SYNOVAX? List the folders first.”
  • “Remember that I prefer metric units. Suggest it to my vault.”
Search is by words

It matches the words you wrote, not their meaning. Titles and tags with the words you would actually ask about make a big difference.

02 · connect your ai2 min

The inbox

When an app learns something about you, it can call suggest_memory. The suggestion is sealed in the connector with your vault's public key, so only your vault can open it.

  1. Open Inbox

    New suggestions show up by themselves within 30 seconds (and as soon as you come back to the tab). Refresh checks right away.

  2. Read, edit, decide

    Fix the wording, choose the folder and tags, then press Approve to save it, or Remove to throw it away.

The vault also checks a vouch: a signature over its inbox key made with a secret only the vault and the app share. If anyone swapped that key on the server to read suggestions, the check fails and the suggestion is refused.

03 · stay in control3 min

Change or revoke access

Under Apps, each app shows what it can read, whether it may suggest, and when it was last used.

  • Edit access to tick or untick folders, then Save access. Unticked folders stop being handed out on the next request, and each one gets a new key: every memory in it is re-encrypted in your browser, and only the apps that still have access receive the new key.
  • Revoke to cancel the key. The very next request with it fails, and the folders it could read get new keys too.
  • Open a folder and press Replace key to do the same by hand at any time.
Revoking is not erasing

An app that already read a memory may have kept a copy in its own history. The new folder key protects everything written from now on; it cannot take back what was already read.

03 · stay in control3 min

The read log

Every app action is a line: the app, the action (folders, list, read, suggest), the memory id when there is one, and the time.

  • Pending lines wait for the end of the current period.
  • Sealed lines belong to a published seal. Press Verify #<seal> and your browser recomputes the line's hash and checks its proof against the public root.

If anyone changed, removed or reordered a line after sealing, the proof no longer leads to the root, and verification fails. Level 04 shows the math.

The seals themselves form a hash chain: each one includes the hash of the one before. Your browser remembers the newest chain hash it has seen, and every time you open the read log it checks the chain still leads from there to the newest seal. If the server rewrote or dropped an older seal, you see ✗ instead of ✓ Seal chain intact. A server owner can also post every seal to a webhook (SEAL_PUBLISH_URL) so a copy lives somewhere the server cannot edit.

03 · stay in control3 min

Passphrase, recovery, export

Change passphrase

Settings → Change passphrase. Every other signed-in session is signed out and the old passphrase stops working.

Forgot it?

On the sign-in page choose Recover, enter the vault name, the 24 words and a new passphrase.

Two-step sign-in

Settings → Turn on two-step sign-in. Add the setup key to an authenticator app (Google Authenticator, Aegis, 1Password…) and type its 6-digit code. From then on, opening the vault asks for a code after the passphrase. Each code works once. Recovering with the 24 words turns it off, in case the phone is what you lost.

Signed-in devices

Settings → Signed-in devices lists every place the vault is open, with browser and system, and lets you sign out any of them or all others at once.

Import

Settings → Import. Paste what another assistant remembers (ChatGPT: Settings → Personalization → Manage memories; Claude: Settings → Memory), one fact per line, or choose a file this vault exported. Duplicates are skipped; everything is encrypted on your device before it is sent.

Export

Settings → Download export saves every folder and memory as one JSON file, decrypted on your device. Store it somewhere safe: it is plain text.

Delete everything

Settings → Delete everything removes the vault, memories, app keys and read log. Type the vault name to confirm. Public seals stay, because they reveal nothing.

Sessions last up to 7 days. Reloading the vault page locks it, because keys live only in the page's memory.

On a phone: open /vault/ in the browser and choose “Add to Home Screen” (Safari) or “Install app” (Chrome). It opens full screen like an app.

04 · security model5 min

The key hierarchy

Every key is made and used in your browser (or in the connector on your machine). The server stores wrapped keys it cannot open.

keys
passphrase ──PBKDF2-SHA-256 × 600,000──▶ master ──HKDF──▶ authKey  (sent; stored as a hash)
                                                   └──HKDF──▶ kek      (never leaves the device)
24 recovery words ──HKDF──▶ recovery master ──▶ authKey / kek            (the backup path)

vault key   random · wrapped with kek and with the recovery kek
folder key  random · wrapped with the vault key, and with each granted app's wrap key
memory      AES-256-GCM with its folder key · AAD binds the ciphertext to its id
inbox       ECDH P-256 key pair · apps seal suggestions to the vault's public key
app key     vlt_app.<id>.<secret> ──HKDF──▶ auth (stored as a hash) / wrap / vouch
  • Why AAD: a ciphertext moved to another memory id refuses to decrypt, so the server cannot swap memories around.
  • Why per-folder keys: granting an app a folder means wrapping just that folder's key for it. Other folders are never unlocked for it.
  • Why the slow derivation: the server stores a hash of authKey. Anyone who steals it still pays 600,000 rounds per guess.
04 · security model2 min

What the server sees

It can see
  • Your vault name
  • How many items there are and how big
  • Times of requests
  • Which app read which memory id, and when
It cannot see
  • Titles, text and tags
  • Folder names and app names
  • What the AI searched for
  • Any key

Deleted rows are overwritten on disk (secure_delete), not just unlinked. Pages are served with a strict content security policy, so only scripts from the site itself can run.

04 · security model4 min

Threat model

If someone…they get
steals the databaseCiphertext and wrapped keys. No key to open them.
runs the serverThe metadata above. Not titles, text, tags, folder names or searches.
guesses passphrases onlineRate limits: 20 logins a minute per address, 10 a minute per vault.
guesses offline from a stolen hash600,000 PBKDF2 rounds per guess. A long passphrase makes this hopeless.
steals an app keyOnly that app's folders, until you revoke it.
swaps your inbox keyNothing: the vouch check fails and the suggestion is refused.
edits the read logA root that no longer matches; every affected proof fails.
injects a script into the pageBlocked by the content security policy.
What this does not protect against

Malware on your own device, someone who knows your passphrase, or an app you granted keeping what it read. SYNOVAX has not been independently audited yet; get one before storing other people's sensitive data.

04 · security model5 min

Seals and proofs

Each log line commits to exact bytes, including a random salt so the hash reveals nothing on its own:

shared/merkle.js
leaf = SHA-256( 0x00 ‖ JSON.stringify([id, ts, vault_id, app_id, action, target, salt]) )
node = SHA-256( 0x01 ‖ left ‖ right )
// an odd node at the end of a level moves up unchanged

The different prefixes stop a leaf from being passed off as a node. A proof is the list of sibling hashes from your leaf up to the root, each marked left or right. Check one yourself in the browser console on the vault page:

browser console
const { leafHash, verifyProof } = await import('/shared/merkle.js');
const leaf = await leafHash(entry);           // entry: the log line's fields
const ok = await verifyProof(leaf, proof, root);
// proof: GET /api/log/:id/proof · root: GET /api/seals/:seq

Seals are public at /api/seals. Today they live on the same server; publishing roots somewhere nobody can edit is on the roadmap.

Put it behind HTTPS

Online, always use HTTPS. Either set TLS_CERT and TLS_KEY (or TLS_PFX), or put a reverse proxy with TLS in front and set TRUST_PROXY=1. If the proxy runs on the same machine, keep HOST=127.0.0.1. For example with Caddy:

Caddyfile
vault.example.com {
  reverse_proxy 127.0.0.1:8787
}
Set TRUST_PROXY behind a proxy

Without it, every request seems to come from the proxy, so per-address limits are shared by everyone. Do not set it when clients reach the server directly: they could then fake their address.

Backups

The server writes a consistent copy of the database to DATA_DIR/backups every 6 hours and keeps the newest 14. Copy that folder to another disk or machine: a backup on the same disk does not survive the disk. A backup is still ciphertext: useless without passphrases, but it does include metadata. To restore, stop the server and put a backup in place of vault.db (delete vault.db-wal and vault.db-shm).

The admin panel

/admin/ publishes the $SYNOVAX token details to the landing page. Its key is in DATA_DIR/admin-key, read it with Get-Content data\admin-key. New contract addresses must be confirmed by typing their last six characters; every change is logged. Sessions last 12 hours and end on restart.

05 · expert3 min

The connector

connector/index.js is an MCP server over stdio. It reads two environment variables:

VariableMeaning
VAULT_APP_KEYThe app key from the vault. Required.
VAULT_URLServer address. Default http://127.0.0.1:8787.

From the key it derives three secrets: one to sign in as the app, one to unwrap the folder keys it was granted, and one to check the inbox key's vouch. It then decrypts locally and hands the app plain text. Run it by hand to see errors:

powershell
$env:VAULT_APP_KEY = "vlt_app.<id>.<secret>"
node connector/index.js

It waits for MCP messages on stdin; that silence means it started. Errors go to stderr.

Search by meaning (optional)

Run npm install once in the vault folder and the connector also searches by meaning, in any language: “what medicine should I avoid” finds “I am allergic to penicillin”, and “when am I most productive” finds “I do my best work before nine”. The model runs on your computer; no memory text leaves it. The only network use is downloading the model once into .cache/models.

VAULT_SEMANTICModelTrade-off
bge-m3 (default)BGE-M3Most accurate (14 of 14 on the test set). About 560 MB on disk, 1 GB of memory, 0.12 s to index each memory.
e5-smallmultilingual E5 smallAbout 130 MB and much faster, but less accurate, especially on vague questions.
offnoneWords only.

The index of what the app may read is saved in .cache/index, encrypted with a key from the app key, so a restart does not index again. Each result is labelled strong, possible or words: no model can say for certain that nothing is relevant, so the AI is told how sure each match is. Without npm install the connector quietly keeps its word search.

05 · expert2 min

Testing

terminal
npm test

31 end-to-end checks against a real server in a throwaway data folder, a “browser” built from the same crypto module, and the real connector spoken to over MCP. Then npm run test:ui drives the real pages in headless Chrome or Edge (17 flows, from creating a vault to recovering it) and fails on any JS error, CSP violation, failed request or page that scrolls sideways on a phone. Among the checks:

  • AES-GCM refuses a wrong context or a single flipped bit.
  • An app sees only its folders; a removed folder or revoked key stops it.
  • A swapped inbox key is caught by the vouch.
  • Every sealed read verifies; a forged one does not.
  • The raw database file contains no plaintext.
  • Pages carry a strict CSP and path tricks return 404.
05 · expert4 min

Troubleshooting

The AI app shows no SYNOVAX tools

Check that the path in args is absolute and points at connector/index.js, that node is on the app's PATH (or use the full path to node), then fully restart the app. Run the connector by hand to see its error.

“VAULT_APP_KEY is not set”

The env block is missing or misspelled in the app's config. It must contain VAULT_APP_KEY.

“This app key was revoked or is not valid”

The key was removed under Apps, mistyped, or belongs to another server. Make a new key and replace it in the config.

The app finds nothing

It only sees folders you ticked for it, and without npm install search is by words only (it forgives plurals, one typo and common synonyms, but not a different idea). Run npm install in the vault folder for search by meaning. Check its folders under Apps and use the words you would ask with in titles and tags.

I lost the phone with my authenticator

Use Recover with your 24 words. That opens the vault and turns two-step sign-in off; turn it on again with the new phone in Settings.

The port is already in use

Something else runs on 8787. Start with another port, then use that port in VAULT_URL too:

powershell
$env:PORT = "8790"; npm start
I forgot my passphrase

Use Recover on the sign-in page with your 24 words. Without them, the vault cannot be opened by anyone.

Unlocking takes a moment

That is the 600,000 PBKDF2 rounds running in your browser. It is the same work an attacker has to do for every guess.

05 · expert2 min

Limits and roadmap

Known limits today
  • Not independently audited
  • Search by meaning needs npm install and works in the connector only, not in the vault page
  • On vague questions the right memory is in the top 3, not always first
  • The seal chain is only as strong as its witnesses: your browser, and a webhook if one is set
  • An app can keep what it already read
Being considered next
  • Passkey sign-in (WebAuthn PRF)
  • Search by meaning in the vault page
  • Sharing a folder between vaults
  • Browser extension
  • Native phone app
